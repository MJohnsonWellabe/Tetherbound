# R9.3 — Scope final performance on target hardware

## Goal
Turn the placeholder **"Performance on target hardware"** into a measured exit-quality performance audit for the shipped ROG Ally / Windows build. Do not optimize from old profiling data or vague impressions.

## Coordinate existing work
Before profiling, read current results from PERF1/PERF2, RG25 boot measurement, vegetation/collision-streaming work and any later performance notes. Those numbers have moved repeatedly as the corridor/content changed. Historical measurements are context, not the baseline.

## Target and scenarios
Profile the current exported Windows build (or the closest reproducible Ally-equivalent harness) at the project's normal 1920x1080 settings across representative real gameplay:
1. title -> new/load boot;
2. starting village;
3. dense wild population/nest area;
4. long traversal through Bands 2–4;
5. river/relay area;
6. stronghold approach and stronghold interior;
7. wild combat and trainer/boss combat;
8. build-heavy player home if a representative save exists;
9. day/night transition;
10. menu/full-map use.

## Metrics
Capture at least:
- average FPS/frame time;
- meaningful low-percentile/stutter indicator (1% low or worst-frame distribution, whichever tooling supports honestly);
- CPU vs GPU indication where available;
- memory/shared VRAM pressure;
- scene/streaming hitch timing;
- boot/load timings from RG25 instrumentation;
- node/draw-call/instance counts when diagnosing a hotspot.

Do not invent a universal FPS target if canon does not specify one. First document measured behavior and identify moments that are visibly disruptive on target hardware. If a target is needed for exit criteria, choose a reasonable tunable target and record it explicitly rather than smuggling it in as an old rule.

## Root-cause workflow
For each material hotspot:
1. reproduce at a fixed location/state;
2. measure baseline;
3. isolate dominant subsystem (Terrain3D, vegetation instancing/collision, creatures, UI, lighting/shadows, stronghold geometry, streaming, scripting, etc.);
4. make the smallest quality-preserving change;
5. remeasure under the same scenario;
6. verify no visual/gameplay regression.

Prefer data/streaming/LOD batching changes over deleting meaningful world content. The goal is the same game running well, not an empty benchmark scene.

## Performance-sensitive invariants
Preserve:
- RG20's world should still feel populated with creatures;
- RG23 substantial objects retain correct collision;
- visual quality bar remains coherent with key art;
- shadows/foliage cannot simply be disabled globally without visual evidence/tradeoff approval;
- long 8192m corridor must stream safely;
- save/load and world persistence remain correct;
- no new hidden pop-in blocker or late collision caused by aggressive streaming distances.

## Deliverable
Produce a performance report plus a prioritized queue of concrete remaining fixes. Each item names:
- scenario/location;
- before measurement;
- bottleneck evidence;
- proposed change/seam;
- expected benefit;
- quality/correctness risk;
- acceptance measurement.

If current performance already meets an acceptable play bar, close with evidence rather than manufacturing optimizations.

## Regression coverage
Where a performance fix changes streaming/instance counts or initialization, add a cheap regression/invariant when possible (e.g. maximum duplicate population, collision residency at player speed, no repeated world construction) without turning CI into a benchmark that flakes on shared runners.

Performance numbers themselves should be collected on controlled/target hardware, not asserted as strict CI wall-clock thresholds.

## Acceptance criteria
1. Current exported build has a documented performance baseline across representative Meadows scenarios.
2. Boot numbers are current and reconciled with RG25.
3. Material stutters/slow areas are tied to measured subsystems, not guessed.
4. Any optimization has comparable before/after evidence.
5. World density, collision and visual identity remain intact.
6. No fix merely raises a timeout or hides work behind an unresponsive screen.
7. Remaining performance work, if any, is a finite prioritized queue with measurable acceptance criteria.

## Definition of done
R9.3 replaces a vague performance heading with a target-hardware evidence set and leaves the Meadows in a state where performance decisions are based on **where the current game actually stalls on the Ally**, not on stale numbers or empty-scene benchmarks.
