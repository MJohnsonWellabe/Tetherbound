## K2 — a continuous fresh-save run from waking to legendary, no developer intervention

**Verdict: CANNOT BE FULLY DETERMINED — no such run exists yet on `main`.** Two
necessary sub-properties were measured directly, and one of them surfaced a real
gap.

### K2a — fresh-save boot repeatability

**The test.** `tests/smoke_title_new_game.gd` and `tests/smoke_title_load_game.gd`,
each the production seam (real title scene, a physical joypad press through the
real `InputMap`, no shortcuts), each run 3 times.

**Results, first pass:**

| test | run1 | run2 | run3 |
|---|---|---|---|
| `title_load_game` | PASS | PASS | PASS |
| `title_new_game` | **FAIL** | **FAIL** | **FAIL** |

`title_new_game`'s failure was deterministic and looked alarming — *"Start New
Game did not transition from title to Meadows"* plus three cascading
state-leak assertions. **Traced to ground, and it is not a game defect.**

`title_screen.gd::_new_button`'s handler (`scripts/ui/title_screen.gd:296-306`)
checks every save slot; if **any** exists it shows a confirmation screen
(*"Start a fresh game?"*) requiring a **second** press of "Start Fresh Game"
before transitioning — correct, deliberate production behaviour, guarding an
existing save from an accidental wipe. `smoke_title_new_game.gd` presses the
title's focused button exactly once and asserts the transition completes from
that one press, which is only true when `user://saves/` is empty; it never
redirects `Game.save_system` to an isolated directory the way its sibling
smoke tests do.

`user://saves/slot_0.json` (the real default autosave slot) existed in this
session at the time of the failing runs, dated within the same session
(`/root/.local/share/godot/app_userdata/Tetherbound/saves/slot_0.json`,
written 22:07, modified 22:17 — inside this run's own window). Its source:
`tests/smoke_authored_camps.gd`'s rest sequence calls the shared
`night_rest.gd` autosave path and, like `smoke_gate_b_continuous.gd` and
`smoke_gateb_flags.gd`, never sets `save_system` to a test-local directory
either — three smoke files write through the **real default save location**
where every sibling save/persistence smoke test uses an isolated `TEST_DIR`.

**Confirmed by direct reproduction:** wiped
`/root/.local/share/godot/app_userdata/Tetherbound/saves/`, re-ran
`smoke_title_new_game.gd` — **PASS**, exit 0, `"title new game: OK -- physical
pad activation reset live state and entered Meadows"`
(`ralph/reports/audit/K-evidence/title_new_game-clean-run1.txt`). The New Game
production path itself is correct; the failure was three composed harness
bugs, none of them game code:

1. `smoke_authored_camps.gd` / `smoke_gate_b_continuous.gd` / `smoke_gateb_flags.gd`
   don't isolate `save_system` and can leave a real autosave in the developer's
   default save slot.
2. `smoke_title_new_game.gd` doesn't isolate `save_system` either, so it is not
   hermetic against exactly that pollution, and asserts only the zero-existing-
   saves branch of a two-branch production flow.
3. **`smoke_title_new_game.gd` is not wired into `ci.yml` at all** — only
   `title_load_game` is (`ci.yml:841`, `verify-owner-regressions-shard`). So this
   specific chain has never been exercised in CI in either direction, and the
   New Game front door — the very first input a fresh player gives the game —
   currently has **no CI coverage**, hermetic or otherwise.

This is exactly the shape `ralph/MEADOWS_EXIT_CRITERION.md`'s K4 warns about:
two individually-plausible test additions (an autosave call; a single-press
assertion) that only produce a wrong signal in combination, and nobody was
watching for the combination because the two files were never run back to
back in the same session before. Left open for whoever owns `tests/`:
redirect `save_system` in all three offending files, and add
`smoke_title_new_game.gd` to `ci.yml`.

Evidence: `ralph/reports/audit/K-evidence/title_new_game-run{1,2,3}.txt`
(failing, polluted), `title_new_game-clean-run1.txt` (passing, isolated),
`title_load_game-run{1,2,3}.txt` (passing throughout).

### K2b — save/reload integrity, mid-session

**The test.** `tests/smoke_save_persistence.gd` — real production opening
through the starter picker and name prompt, Mira's one-time gift, two physical
one-shot pickups, an exact pose/camera save at an arbitrary wilderness point,
a scrambled live state, a load, then a **full world teardown and
reconstruction** with the loaded state still resident (proving Terrain3D's
async startup cannot silently overwrite the saved pose — the exact class of
bug the title-before-world race could produce). Backed by
`tests/test_save_format.gd`, 48 unit tests / 221 assertions covering every
save-version migration path.

**Result:** both green.
`ralph/reports/audit/K-evidence/save_persistence-run1.txt` —
`"PASS: exact pose, opening/starter, Tam gift, TM/key one-shots, and controls
survived a real Meadows save/load"`.
`ralph/reports/audit/K-evidence/test_save_format-run1.txt` — `48 tests, 221
assertions, 0 failed`.

**The coverage gap, stated plainly.** This is the **only** played-path
save/reload round trip in the repo, and its round trip happens at one
arbitrary point mid-opening — not at a chapter-gate boundary (post-practice-
fight, post-road-gate, post-Warden, post-legendary). K2 asks for integrity
"across gates"; nothing in the repo currently saves and reloads *at* a gate
transition specifically, only mid-segment. `test_save_format.gd`'s 48 tests are
real coverage of the **format**, exercised through hand-built `FakeGame`
doubles, not a played path — strong for "a version bump does not brick an old
save," silent on "the moment the road gate opens is a moment a save survives."

**What it would take to close.** Add a save/reload checkpoint at 2–3 gate
transitions to the `GATE-F-FULL` chain (or as small standalone smoke tests
following `smoke_save_persistence.gd`'s pattern) — a played segment, not a
config check, per the evidence rule.

## K3 — no major core-verb reliability failures across the run

**Verdict: ONE confirmed open defect, real and reproducible; the "family" this
lane was briefed to measure turns out to be two closed items and one open one,
not three of a kind.**

### The brief's premise, checked against the record

The brief asked this lane to treat three sightings — T5-CARE's build-verb
lockout, `party_count_after_catches`'s "engage" failure, and
`smoke_authored_camps`'s `trail_camp` flake — as one arbiter-prompt-press
family. `ralph/reports/handover-LAND-FIX-2-2026-08-30.md` had already
investigated this exact grouping and found it wrong in two of three cases,
**before** this lane started:

- **T5-CARE's build-verb lockout was a real arbiter defect** (an actionable
  gather offer stole the interact press from Build) — **and it shipped fixed**,
  in `playground_hud.gd::_hammer_opens_the_catalogue()`, per
  `ralph/reports/handover-T5-CARE-2026-08-30.md`.
- **The `party_count_after_catches` "engage" failure was never an arbiter bug.**
  LAND-FIX-2 traced it to a village fence panel blocking the walk to one of
  three practice-cluster bramblebuns — the straddle defect
  `ralph/reports/PARTY_COUNT_STRADDLE_2026-08-30.md` measured and `main`
  commits `5cc2819e`/`453107fb` fixed by moving the boundary outline.
- **Only `smoke_authored_camps`'s `trail_camp` press is the actual "prompt
  offered, press does nothing" defect**, and it is still open.

So the grouping this lane was asked to measure is stale as a family — two of
its three members already have closed, unrelated root causes. Measuring it as
one family would have hidden that two-thirds of it is done. Reporting each
member on its own evidence, below.

### `smoke_authored_camps` at `trail_camp` — OPEN, confirmed at 25% (2/8)

**The test.** `tests/smoke_authored_camps.gd`, run 8 times locally, isolated
processes.

| run | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| result | PASS | PASS | PASS | **FAIL** | PASS | PASS | PASS | **FAIL** |

**2/8 = 25%**, matching the coordinator's own 2026-08-30 measurement of
1-in-4 exactly. Both failures carry the identical signature:

```
trail_camp    offers 'Rest until morning'   (all 5 camps' offers succeed first)
  FAIL: pressing interact at 'trail_camp' activated nothing
```

This happens in the test's **second** pass at `trail_camp` — the
`_resting_at_an_authored_camp_passes_the_night()` phase, which re-stands the
player at the same point and calls `arbiter.call("activate")` directly rather
than a synthetic press, roughly 20 physics frames after teleporting. The
arbiter's `prompt()` correctly reports the offer moments earlier in the same
run (the first pass, over all 5 camps, always succeeds — including on both
failing runs). A plausible, unconfirmed hypothesis for whoever picks this up:
a one-frame-late refresh of the arbiter's current-offer state after the second
teleport at the same point, which only `trail_camp` exercises because it is
the only camp visited twice (once for the offer sweep, once for the sleep
test) in this file. Not fixed, not further diagnosed beyond what the evidence
supports — this is the one real, open, player-facing "prompt offered, press
does nothing" defect in the set the brief named.

Evidence: `ralph/reports/audit/K-evidence/authored_camps-run{1..8}.txt`.
**Closing cost:** a focused repro with frame-by-frame arbiter-state logging
around the second `trail_camp` visit — a few hours, not a played segment;
`tools/_probe_engage_obstacle.gd`'s style (LAND-FIX-2) is the template for

### Error census — no `SCRIPT ERROR`, an intermittent low-severity engine leak

Every run this lane produced (22 total, `smoke_authored_camps`,
`smoke_party_count_after_catches`, `smoke_title_new_game`,
`smoke_title_load_game`, `smoke_save_persistence`, `smoke_playground`,
`test_band_content.gd`, `test_save_format.gd`) was grepped for `SCRIPT ERROR`,
`Parse Error` and `Failed to load`: **zero, in every run.**

A `WARNING: N ObjectDB instances were leaked at exit` / `ERROR: N resources
still in use at exit` pair appears **intermittently** — 0 in most runs, 6/3,
8/4 or 10/5 in others, same script, same code path, no correlation found with
pass/fail (it appears on both passing and failing `authored_camps` runs, and
is absent from `smoke_save_persistence`'s full-world-teardown-and-reconstruct
run entirely). Never fails a test — Godot reports it as a warning/error pair
at process exit, after `quit()` already recorded the test's own result — and
it is not checked or tracked anywhere in `ralph/conventions.md` or `ci.yml`
today. Flagging it because it is real, reproducible, and currently invisible
to CI (nothing greps for it): a small number of nodes/resources are not being
freed before some `SceneTree` shutdown paths, non-deterministically. Full
table: `ralph/reports/audit/K-evidence/*.txt`, `WARNING:`/`ERROR:` lines.
**Closing cost:** a `--verbose` re-run to name the leaked instances, then a
teardown-order fix — a few hours once reproduced with names attached; not
attempted here per the no-fix rule.

the moment anyone runs these files in the same session — which is precisely
what nearly happened in this audit. Recorded under K2 above rather than
repeated here; it belongs in both.
