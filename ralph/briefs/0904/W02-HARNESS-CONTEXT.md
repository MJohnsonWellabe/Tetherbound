# Lane W02-HARNESS-CONTEXT — the Gate F harness's `input_context` misresolves to `build_catalogue` and never returns (Phase 0.2 / CL-H13)

Branch: `ralph/W02-HARNESS-CONTEXT-0904`. Model tier: root-cause investigation.

**Why.** Confirmed at three independent sites (Oreth on S08, Captain Vance on S07, S08 after Captain Riverwatch): the operator harness's synthesised input reaches `build_shortcut` while the game believes it is in a context where that action is not listed, the Build catalogue opens, nothing closes it, and every later step of the segment runs behind a menu. This corrupts Gate 3's evidence and is why Band 4 has none. Read `docs/FINISH_THE_MEADOWS.md` §0.2, `docs/GATE2_GATE3_CLOSURE_PLAN.md` row CL-H13 and the `CURRENT_STATE.md` §3 P1 row about it. Two shipped guards (`data/config/input_contexts.json` makes `world` and `combat` mutually exclusive; `playground_hud.gd::_world_input_allowed()` refuses during combat) mean a real player cannot reach it — so **the defect is in the harness's own input path** (`tools/gate_f/operator_harness.gd` and whatever it calls to synthesise events), OR in a shared game path that only synthesised events exercise (e.g. an action event that carries both `combat_charged` and `build_shortcut` because they share `JoyAxis:4`, and a consumer that reads `Input.is_action_just_pressed` after the combat guard has already released). Find which, with evidence.

**Do not fix it by** rebinding a key, routing one more step through the mouse device, or editing segment JSON. Those are per-site workarounds and the next segment finds the next site. The existing S07-57 mouse routing stays.

**Owns:** `tools/gate_f/operator_harness.gd`, `tools/gate_f/harness_config.json`, `tools/gate_f/probe_build_catalogue_arm_cause.gd`, new `tools/gate_f/probe_*.gd`, `tests/test_gate_f_rig.gd`, `tests/test_gate_f_instrumentation.gd` (if present). If the root cause is in a game script (e.g. `scripts/ui/playground_hud.gd`'s shortcut handler or `scripts/ui/build_menu.gd`), you may make a minimal fix there ONLY if it is provably unreachable-by-player today and reachable-by-harness, and you must add a test that fails without it — and say so prominently in the report so the coordinator can route conflicts.

**Method.** Write a probe that reproduces the flip deterministically without walking a whole segment: build the S08 synthetic entry (`tools/gate_f/build_s08_entry_synthetic.gd`), stand at Oreth or Riverwatch, run the exact step shape the segment JSON uses (read `S08.json`), and log `input_context` plus every `InputEvent` the harness emits and every action the game reads, per frame. Bisect from the log. Then fix at the mechanism, add a regression test that goes red on the old code, and re-run the reproduction to show it clean. Then run S08 through its first 30 steps (`tools/gate_f/run_segment.sh` in logic mode — see `docs/GATE3_EXECUTION_PLAN.md` §4b for the freeze-record trap) and show the context never flips.

**Acceptance.** The three named sites no longer flip, proven by the probe on the same commit; `test_gate_f_rig.gd` green; a written root cause in `ralph/reports/W02-HARNESS-CONTEXT-0904/REPORT.md` that names the mechanism, and the CL-H13 rows in `docs/CURRENT_STATE.md` and `docs/GATE2_GATE3_CLOSURE_PLAN.md` rewritten to "fixed" with the evidence.
