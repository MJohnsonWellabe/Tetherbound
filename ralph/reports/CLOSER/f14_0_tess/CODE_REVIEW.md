## Findings
1. combat_manager.gd:1156-1160 (with camera_rig.gd:638), severity medium, NOT VERIFIABLE WITHOUT GODOT. The composition yaw changes the camera basis that `planar_basis()` feeds into camera-relative piloting move/aim (combat_manager.gd:3043, :3141, and the aim/throw forward at :1445/:1524). So the stick-to-world mapping in Tess's Mirejaw fight is rotated an extra 35 degrees compared with other fights. It is local input mapping and not authority, and the existing tell swing already does the same (combat.json says so), so it is arguably in-policy. But it is a feel change for that fight, and it is not purely cosmetic. Acceptance should include a piloting check, not only camera frames.
2. combat_manager.gd:1154-1160, severity medium, NOT VERIFIABLE WITHOUT GODOT. Host/guest divergence risk. The yaw and trainer stand read `combat_override` on the local `_wild` body. On a guest or realm-owned opponent (`realm_owned_opponent` path, which calls `_place_realm_owned_ally` and never `_stand_the_trainer_aside`), the proxy body may not carry `combat_override`, or may not have the whole block. The guest would then get the shared 35 degrees while the host gets 70, and only the host's trainer stands beside the ally. Presentation and local input basis only (no shared state), but it means host and guest see different fights. I did not trace whether the guest proxy is given the override. Confirm the guest's `_wild` gets `combat_override`, or accept this as documented "local to each peer" presentation.
3. combat_manager.gd:1186-1195 and camera_rig.gd:638-639, severity low, NOT VERIFIABLE WITHOUT GODOT. The tell swing adds `composition_extra_deg` (config default 40) on top of the authored 70 in the tell moments, so the neutral yaw can reach about 110 degrees. That is past the 100 degree clamp's stated purpose, and it could put the lens near or behind the ally's far end when the arm cannot back off. The `tell_swing_max_gap_m` 7.0 gating limits it, and the judged frames need a look.
4. combat_manager.gd:1041 and :1073-1075, severity low. The far-side-first order assumes the lens swings to +side, which is true only for a positive yaw (`signf(composition)` in camera_rig.gd:639). The `opponent_composition_yaw_deg` clamp allows negative values, so a future negative-yaw opt-in would put the trainer between the lens and the ally. Only Tess Mirejaw opts in today.
5. combat_manager.gd:1041 (the trainer beside the ally, with `_ally_body` placed just before), severity low. The trainer stands only 2.4 m from the ally centre (plus -1.2 m forward), so a very wide ally could overlap it. The overlap check is `_player.test_move`, which only sees bodies on the player's collision mask. I did not verify that creature bodies are on it. No gameplay reads the trainer position during the fight, as far as I read (throw arms with `_player`, but catching is barred against trainer-owned creatures).
6. combat_manager.gd:1158-1160, severity nit. An authored yaw of exactly 0.0 cannot override a nonzero shared or `_opponent_camera` yaw, because 0.0 means "absent". It is documented in wild_creature.gd but not at the call site.
7. tests/test_combat_spaced_camera.gd, severity nit. There is no test of `_stand_the_trainer_aside` or `_take_camera` themselves (the anchor origin, side order and arena bound are untested), only the accessors, the static helper and the data. Also, `WILD.new()` relies on `MATH.config()` loading outside a scene tree. That is very likely fine, since the accessor only reads config, but I did not run it.
