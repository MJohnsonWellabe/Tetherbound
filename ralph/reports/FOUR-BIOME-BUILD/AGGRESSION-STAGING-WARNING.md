# Aggression second-world staging warning

## Observed result

The passing separated-fixture aggression run
(`%TEMP%\aggression-ci-34208280455-separated-fixtures-behavior-20260908.log`)
contains one native warning between the second Meadows construction log and the
aggressive fixture-position breadcrumb:

```text
[player] velocity 854729 m/s exceeded the 120 m/s ceiling at 0.0, 2.1, 0.0; clamped
```

There is no native `ERROR` or `SCRIPT ERROR`, and both later behavior halves
pass. This is therefore not an aggression failure, but neither is the staging
log clean.

## Mechanism

This is the already measured Meadows boot race documented directly above
`player_controller.gd::_clamp_runaway_velocity()` and in commit `cc95a8b70`.
Godot transfers a collider's apparent platform velocity to a
`CharacterBody3D` resting on it. Meadows construction creates or moves large
colliders while Player is already physics-active; moving one thousands of
metres in a physics frame can therefore hand Player a six- or seven-digit
metres-per-second velocity. The 120 m/s clamp was intentionally added as a
general symptom guard after an earlier measured boot launched Player millions
of metres out of the world.

That is a source-supported match to a known measured mechanism, not a newly
identified platform collider. The aggression log records the clamped velocity
and staging position but does not trace which moving collider supplied it.

The current source ordering matches the new log:

- `meadows_playground.tscn` authors Player at world `(0,40,0)`.
- `playground_world.gd::_ready()` adds Terrain3D and explicitly yields process
  frames while its data directory becomes ready, then places Player on terrain
  at `_place_player()`.
- World dressing and settlement construction continue after that placement.
- The warning reports Player at `(0,2.1,0)`, the ordinary world-origin ground
  pose, and occurs before the aggression harness moves the body to its
  disclosed `(40,-72)` fixture. It is not velocity generated by that fixture
  move or its later Galecrest approach.
- `_load_fixture()` does not call `_ensure_ally()` until its 300-frame world
  settle has completed. The risky construction already has a live Player; no
  companion or behavior assertion is required for the mechanism.

The first isolated world did not print the warning and the second did. That is
consistent with a physics/build ordering race, not evidence that the first
world is immune.

## Production reach

The cause is not unique to manually adding a second test scene. The production
Meadows root uses the same `_ready()` sequence. Its existing player hold is
narrow:

```text
held_transition_player = not simulation_only
    and _shell_build.is_slicing() and _player != null
```

`shell_build_budget.gd` explicitly disables slicing for all single-player
builds. Consequently a solo fresh boot, Continue/reload, and solo return to
Meadows can all enter the same construction interval with Player active. A
pending Meadows realm entry disables Player only later inside
`_place_player()`, after the earlier Terrain3D process-frame yields. The
production clamp prevents the historic catastrophic launch, but the new
warning demonstrates that the underlying transfer can still occur.

## Candidate implementation and bounded validation

The candidate preserves Player's process mode, disables its
physics and zero velocity before the first world-build yield, then restore the
mode with zero velocity and reset physics interpolation only after the real
world is completely constructed. That is the same lifecycle already used for
sliced live-session crossings, widened to the unsliced solo build interval;
it is not an aggression-harness navigation change. Simulation-only shells are
explicitly excluded. Restoration changes `process_mode` only; it does not call
`set_physics_process(true)`, so `_settle_meadows_realm_arrival()` retains sole
ownership of a pending arrival's narrower physics hold and Game retains its
existing deferred-completion retry once `shell_build_complete()` becomes true.

Focused pure tests in `tests/test_meadows_player_build_hold.gd` pass 3/3. They
exercise the actual helpers rather than source text:

- a real build disables Player, zeros velocity, restores the exact prior mode,
  and discards construction-time velocity;
- a simulation shell receives no hold token and is not mutated by either call;
- restoring the build hold does not release a separately disabled pending
  arrival.

The existing transition guards also remain green:

- `test_realm_shell_transition_guard.gd`: 3/3;
- `test_realm_entry_readiness.gd`: 7/7.

Runtime proof is still queued behind the active Stormwood world and is required
in all three paths before this can be called fixed:

1. fresh solo Meadows boot;
2. a second Meadows boot/reload in one process;
3. a real solo realm return with an authored pending entry.

Each must retain the authored final position, end with no pending entry, allow
grounded/actionable movement after release, and produce no runaway-velocity
warning. Multiplayer shell/sliced-transition tests must also remain green so
the broader hold does not disturb their existing mode restoration. No runtime
claim follows from the focused tests above.
