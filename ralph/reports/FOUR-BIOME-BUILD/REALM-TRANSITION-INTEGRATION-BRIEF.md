# Production realm-transition integration brief

2026-09-09. **Design for review; no production edits authorized by this document.** The desired outcome is that a connected client can cross from Meadows to Water through `Game.enter_realm` without destroying remotely tracked bodies before consuming their host despawns, while the host and other players continue normally. The same integration must preserve host crossings, solo, existing save compensation, and disconnect behavior.

The basis is the exact new PR94 native error, the native negative/control proof, and the corrected three-peer protocol's29 passing checks with zero native errors. See [protocol proof](REALM-DESPAWN-PROTOCOL-PROOF.md). That candidate is a mechanism proof, not the production fix.

## Decision on scope

**Include host transitions in the transaction now.** A client-only branch can preserve the old host code text, but adding admission/receiver-ready state globally while leaving host scene replacement outside it creates an inconsistent lifecycle and can regress host crossings. The current host path destroys its authoritative current scene, and may destroy an already occupied destination shell; both have spawners observed by other clients. Those observers must consume the relevant despawns before their source spawners are replaced. Do not silently disable host crossing or advertise unchanged known-broken ordering as preservation.

Use a finite host-coordinated transition transaction for all live-network crossings. Client-only crossings scope quiescence to that departing observer and its retiring owned bodies. Host crossings additionally enroll every observer of each authoritative realm subtree that will be replaced (old host world plus an existing destination shell). Those affected proxies briefly disappear and reappear after their replacement spawner is ready; unrelated realm observers remain enabled. Their local gameplay scenes remain present. This follows the existing scene-rebuild architecture without introducing an unproven live-scene-to-shell adoption system.

Serialize transitions whose affected realm subtrees overlap, not every gate in the game. A second crossing waits asynchronously while its current scene remains live; do not create a nested registry mutation. Maximum participants remain the existing four. Admission gating is network presentation/lifecycle state, never persisted progression or a new realm id.

## Current source inventory that sets the minimum

- `autoload/game_state.gd::enter_realm` is already asynchronous. It changes `current_realm`, announces before scene replacement, saves on host, awaits destination readiness, and has compensating-save/scene rollback. Session's comment calling it synchronous is stale.
- `scripts/net/session.gd::announce_realm/_rpc_realm_changed/_apply_realm_change` currently commits realm membership immediately; its ledger channel1 is not a barrier for Godot's scene replication channel0.
- `scripts/net/trainer_spawn.gd::_spawn_trainer` gives its State/Sync authority to the represented peer. Engine spawn visibility ignores synchronizers not authoritative on the host. Therefore its current comment claiming that this one peer-owned filter also gates host spawning is false for remote-owned trainers.
- **CreatureSpawner is active**, not a future placeholder. Shared `scripts/combat/encounter_director.gd::_wire_creature_replication` wires it; `_spawn_deployed_creature` constructs a peer-owned Sync. All biome directors inherit that path. Its `_session_peer_ids` is currently not realm-filtered. A trainer-only drain leaves deployed proxy receive-map entries behind.
- Four authored worlds contain TrainerSpawner, CreatureSpawner, and ItemSpawner. Repository search finds no active ItemSpawner spawn-function/writer. The adapter must nevertheless inventory every active spawner in the replaced subtree, including empty ones, rather than assuming two names exhaust runtime replication.

## Transient state and authentication

Host owns a monotonically increasing transition id scoped to a fresh session epoch; identity is `(session_epoch, mover_peer_id, transition_id)`. Store source realm from the host registry, validated destination from existing configured realm ids, affected realm/spawner generations, phase, expected sender→receiver pairs, receiver inventories, and a phase deadline. Never trust client-supplied from-realm, mover id, expected peers, or body paths. The reliable request's remote sender owns only its own crossing.

Suggested phases: reserved → quiescing → draining → detached/awaiting-ready → admitted; cancelling → restored, or session-ended. Every handler verifies epoch/token, expected phase, and actual RPC sender. Duplicate matching messages are idempotent; stale/wrong-peer readiness and acks cannot advance state. A connected missing acknowledgment at the bounded deadline causes cancellation/recovery, not a synthetic success or removal from the expected set. Use the existing realm-load deadline as an outer bound; introduce no arbitrary successful sleep.

Each body's immutable spawn metadata includes realm, spawner generation, represented owner, and stable logical body id. State Sync keeps that owner's authority. After the existing recursive authority assignment, add an empty-property `AdmissionSync` with explicit authority1 **before the body enters the tree**. Its host filter controls spawn/despawn; the State Sync's local-owner filter controls outgoing state recipients. For host-owned bodies both host-authoritative synchronizers participate in engine OR visibility, so both filters must agree when denying admission. A hidden AdmissionSync cannot override a still-visible host State Sync.

Initial spawn admission requires a known registry peer and an adapter-ready receiving realm/generation, except the host's proven ready authority shell. Replace the current unknown-row-visible shortcut with explicit late-join readiness plus a visibility refresh on readiness; otherwise a first spawn can target a missing path. This means tests must cover late join and shell boot, not just gate crossings.

## Departure and arrival ordering

1. Game validates the destination and snapshots/syncs existing state. Reserve affected subtrees **before** setting `current_realm`; this prevents RealmShells' periodic reconcile from tearing down the destination shell during save preparation. The reservation keeps paths alive but does not yet delete bodies.
2. Preserve host autosave behavior. If it refuses, restore the original state and cancel the reservation while the old receiver still exists. No irreversible network detach should have occurred at this point.
3. Begin quiescence. Build inventory from every registered spawner and enumerate actual sender→observer traffic affected by this replacement. Gate new spawns into those receivers. Each authority suspends only the relevant outbound recipients, then emits its own reliable **channel0** fence. Trainer body RPCs already using reliable0 share that order; scene-bound ledger1 deployment/recall traffic needs its own channel1 fence/gate before destroying that director. A ledger1 ack cannot fence channel0 or another sender.
4. Host waits for authenticated receiver acknowledgments of all expected sender fences. Continuous unreliable sync is not credited as reliably ordered; missing synchronizers are tolerated by the installed engine, but no found-with-invalid-root interval is permitted. The actual native error set must remain empty for the targeted path.
5. Host hides all affected bodies from departing/replaced receivers through AdmissionSync, and retires only bodies whose owner is leaving that realm. For a host authoritative subtree replacement, drain all observers of that subtree. The engine visibility handler synchronously enqueues reliable0 despawns; host follows with its reliable0 fence. Other observers of retained subtrees continue receiving state.
6. A receiver reports drained only after actual spawner `despawned` callbacks emptied its inventory and the host fence arrived. Include new spawn callbacks until the admission gate/fence makes that inventory closed. Confirm actual spawn parents have no remaining replicated bodies. Never free a received body locally to make the count reach zero.
7. Commit destination realm membership internally with receiving admission still closed. Host may stand up the destination authority shell under the existing build-serialization rules. Game replaces its old scene only after the coordinator grants detach; pins prevent old authoritative spawners from vanishing before all affected observers drained.
8. Game's existing scene-ready check plus all active spawner adapters being wired establishes local receiver-ready. Host's target authority adapter must also be ready. Only then enable destination admission, refresh visibility, and release obsolete pins. Existing `complete_realm_entry` remains responsible for player placement/entry completion.

## All-spawner enrollment and failure behavior

The shared helper recursively registers MultiplayerSpawners under each authoritative/receiving realm root and their actual spawn parents. Trainer and deployed-creature spawn functions attach its metadata and AdmissionSync. Empty ItemSpawner contributes zero bodies but remains watched. Any nonempty unregistered/unsupported active spawner is a pre-detach failure with an exact diagnostic; do not destroy the subtree and claim success. Implement a new active kind only when its existing writer is found, not speculative item replication.

Deployed creature announcements are tied to director/realm, so realm filtering must preserve current local deployment reannouncement in the destination and keep every other owner's actual party untouched. Temporary proxy despawn is not recall of an owned creature, encounter defeat, contribution loss, or a reward.

Before detach, cancellation restores outgoing/admission gates on still-live receivers and re-reconciles expected proxies. After detach, rebuild the prior receiver using existing rollback, await its adapter readiness, then admit it with a new generation. Preserve compensating-save failure's guarded overlay and persisted recovery state; never advertise receiver-ready while that recovery is unresolved.

Actual `peer_disconnected` removes that peer's required sender/receiver acks and triggers existing host-owned body/encounter cleanup; it does not remove a still-connected peer merely for being slow. A disconnected mover cancels its reservation and releases pins after surviving observers drain what remains. Host loss uses the existing save-character/session-ended/title route; resolve pending awaits as cancelled so Game cannot later replace the title with a stale destination. No host migration. Solo/no-active-session is an immediate coordinator no-op and retains its existing scene/save behavior.
