# Independent review: F33#3 trainer-gear hazard mitigation (0ba8f1bc, 51aae71e)

Reviewer: independent agent review, code-read only. Godot is not installed in the review container, so neither smoke was re-run here. The verdict relies on reading the source and on the commit's reported runs (12/12 and 8/8).

**Verdict: APPROVE-WITH-NITS**

## Hook correctness

- `scripts/player/swim_controller.gd:173-176`: the flow is scaled by `current_push` before velocity is composed. The skills activity record at :182 subtracts `flow * delta` using the same scaled `flow`, so it still removes exactly the current's share of the displacement and stays consistent. The drowning mitigation at :199-201 runs once per frame after `state.advance` and before the death check, so it is not applied twice. Nothing else calls `mitigate_hazard_damage`.
- `scripts/world/water.gd:352-356`: the mitigation runs after the dead-check and before the clamp. The `died` emit is unchanged. Correct.
- `scripts/player/player_vitals.gd:162,170`: `env_regen_scale` is clamped to [0,1], applies only on the regen branch and multiplies the existing D29 hunger and buff scale. It never touches sprint drain and never makes stamina go down. Correct.
- `scripts/player/player_controller.gd:230-236, 314, 1051`: both call sites now pass `_cold_regen_scale()`. The swim and fly branches return before `vitals.tick`, and they had no regen tick before either, so nothing changed there.
- `scripts/world/stormwood_dynamo.gd:565-574`: `static_duration_scale()` is clamped to at least 1 - mitigation_cap (0.4), so the duration is never 0 because of gear. The new `duration > 0` guard matches stormwood_lightning.gd:243. The only change for a player without gear is when the config sets `static_seconds <= 0`. Before, that case wrote a 0-second buff, which also cleared an active static. Now it does nothing. The current config uses 8 s, so this has no practical effect.
- `scripts/player/player_equipment.gd:286-290` `hazards_live()`: requires both runtime_enabled and hazards_enabled. It reads the cached config.

## Hard rules, co-op and saves

- The cold zone (gear.json `cold_zones`, Upper Cloudreach, penalty 0.35) slows regen only, to a minimum of 0.65 (0.65 x 0.35 = 0.23 together with severe hunger). It has no meter, no drain and no health effect. Gear eases it but is never needed to recover. This matches SYSTEMS.md:187 and HOMESTEAD.md:103 ("an authored local zone only, never a survival meter"). It does not make camping necessary. The 0.35 is a declared, tunable number in an already-specified design row, so it is not a silent major decision. The trainer never deals damage.
- Co-op: every hook mutates only the local process's own `Player.vitals` and reads its own `Game.player_equipment`. No host-authoritative state is involved. For the Dynamo, the host sends only the base `static_seconds` per peer (stormwood_dynamo.gd:520), and each receiver applies its own gear. That is the same split stormwood_lightning.gd:230-245 already documents. `owner_passive_replay.gd` handles creature actor vitals (hp and faint), not trainer stamina. Trainer stamina is saved only as `stamina_fraction` (save_game.gd:1430-1444) and published as a quantized fraction for swimming presentation (remote_trainer.gd:364-377). Neither can desync from a local regen rate.
- Players with no hazard gear: behaviour is identical except for the new cold-zone regen penalty and the `static_seconds <= 0` edge case above.

## Findings

1. **Low — design-parity inconsistency.** `scripts/world/stormwood_dynamo.gd:566-571`. Scenario: a trainer wears all four Stormglass travel pieces. Each has `storm_strike_reduction` and `static_duration_scale`, so `storm_mitigation()` counts 4 pieces, meets `insulation_pieces_for_immunity: 4` and gives ordinary lightning a static_scale of **0**, which is full immunity. A Dynamo discharge on the same trainer still applies **4.18 s** of static (0.85^4). The comment says the Dynamo shortens static "as ordinary Stormwood lightning already does", but the two paths now give different results for the same set. There are two options. Use `storm_mitigation(...)`'s static_scale here for parity. Or keep it deliberately partial (a boss hazard) and correct the comment and HOMESTEAD §7.
2. **Low — UX legibility.** `scripts/player/player_controller.gd:230-236`. Scenario: a player reaches the Upper Cloudreach heights and stamina recovers 35% slower with no cue. There is no status icon, world message or tooltip, and the Skyglass benefit is invisible. Add a one-time world message or a status chip in the HUD lane. This is not a hard-rule problem.
3. **Low — test coverage of call sites.** `tests/smoke_f33_trainer_hazards.gd:75-93`. The cold check calls `player._cold_regen_scale()` and `vitals.tick(...)` directly with physics turned off. If the `_cold_regen_scale()` argument were removed at player_controller.gd:314 or :1051, every check would still pass. The pond and Dynamo checks call the functions that contain the hooks, and removing those hooks would fail them. The swim smoke does drive the real `physics_step` through `_physics_process`, so it would catch a removed hook. Add one check that turns physics on in the zone at 0 stamina and compares regen over N frames. Separately, the cold zone was proven in the Meadows world with the realm string swapped. No check shows that the AABB actually covers the authored Upper Cloudreach heights on the real route.
4. **Nit — per-frame cost.** `scripts/player/player_equipment.gd:251-266`. `local_cold_regen_scale` calls `cold_regen_scale(0.0)` even outside every zone. That runs `hazard_scale("cold")`, which does 5 slot `definition()` lookups, every physics frame. Return 1.0 early when penalty == 0. The config is cached in `static var _gear_rules` and the JSON is not parsed per frame. One exception: if gear.json fails to parse, the empty cache causes a re-read on every call. That pattern existed before, but this is now a per-frame path. Cache a sentinel instead. One zone loop is negligible.
5. **Nit — declared stat with no consumer.** gear.json Tidesteel rows: `swim_stamina_reduction` (HAZARD_FIELDS "swim_stamina") still has no consumer. `swim_controller` passes the raw `stamina_drain_per_s` into `state.advance`. If the item text or tooltips show this stat, it promises an effect that does not exist. Either wire it under the same flag or record it as open in F33.
6. **Info — test isolation.** Both smokes write `EQUIP._gear_rules`, which is a script-static, through `_set_hazards`. `tools/run_all_smokes.sh` runs each smoke in its own Godot process, so nothing leaks. Neither smoke restores the original config before `quit`. Add a restore if these are ever batched in one process. Equipping does not trigger a save, so the trainer smoke writes nothing to a real user save.

No finding blocks the change. All six hooks are correct, the change stays within the light-satiety and cold rules, and co-op behaviour is consistent because each process applies the effects to its own trainer.
