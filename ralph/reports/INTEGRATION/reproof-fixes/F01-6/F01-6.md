# F01#6: two-peer tournament (`smoke_net_shared_boss.gd --tournament`)

**Verdict: still open. No logic deadlock found. The semi-final fails because both peers run at about 0.3–1 frames per second in this container, and three wall-clock-sensitive paths stop fitting: the join deadline, the vitals fence and the smoke budget.** The fixture-order bug that blocked every guest strike is fixed. Runs 11–14 reach the semi-final, and in run 11 the guest's semi strike also lands.

Command: `godot --headless --path . --script tests/smoke_net_shared_boss.gd -- --tournament`, with `run_net_smoke.sh`'s `TB_NET_*` environment (`run_net_smoke.sh` does not forward `--tournament`). Two Meadows peers ran on the 4-core container, uncontended (load average about 1.5).

## What the instrumentation measured

1. **The host answers a join quickly.** `_host_commit_encounter(engage)` takes 58 ms (quarter) and 159 ms (semi) (`run11-engage-timing-and-long-frames.txt`). An earlier run measured the guest seeing the verdict 2.6 s after asking in the quarter-final. In the semi-final, the 5 s deadline (`multiplayer.json` `shared_opponent_join_timeout_s`) cancelled the join 160 ms before the ok verdict arrived. The guest then disengages.
2. **Frames take 0.4–3.5 s on both peers** throughout the tournament (`run12-frame-breakdown.txt`):
   - Each Meadows world holds about 184,000 nodes and 245,000 objects.
   - During a fight the host's physics step rises from about 10 ms to 250–320 ms.
   - Every frame runs 8 catch-up physics steps, the cap.
   - Typical host frames are about 3 s: about 1 s of process plus 8 × about 300 ms of physics.
   - An RPC round trip spans several frame boundaries, so it takes 3–6 s of wall time.
3. **No vitals proposal is lost** (`run14-vitals-ack-path.txt`). Every proposal staged by an enemy hit is committed, applied by its owner, accepted by the host and presented. A guest-owned proposal takes about 1.5 s in run 14 and 4–19 s in run 13 (`run13-vitals-proposals.txt`). That is the host save, then the guest apply and save, then the ack RPC, then the host accept and save, then the retry: about 5 frame boundaries plus three disk writes.
4. **The fence covers the whole encounter.** `ordinary_actor_vitals_pending(id)` refuses `move_start`, `strike_intent`, `burst_intent` and `disengage` for **every** participant while any proposal in that encounter is unpresented (`encounter_director.gd` `_host_commit_encounter`). With enemy hits landing every few seconds and each fence held for 4–19 s, a 6-attempt strike leg can see the fence the whole time. That is run 12.

## What is not the cause

- The host processing the engage: it takes 58–159 ms.
- A permanently stuck vitals proposal: all of them resolve.
- Container contention: the load average was about 1.5 on 4 cores, with the peers alone.
- The earlier `pending_vitals` hypothesis (run 9): proposals resolve; they are just slow at this frame rate.

## Open decisions (not changed on this lane)

Each option changes a product number, a hot file or the run environment. None is a test-side fix.

1. **Run environment:** the tournament leg needs a runner where two Meadows peers hold usable frame rates. It cannot pass here without widening a deadline.
2. **Performance work order:** the 184k-node Meadows world, and the roughly 30× physics-step cost during a tournament fight, on the host and the guest. A per-callback profile was not taken; a repo-wide temporary timing edit was declined, so the hot callback is not yet named.
3. **Join deadline semantics:** `shared_opponent_join_timeout_s` is 5 s of wall time. At these frame rates a live, answering host can miss it. A deadline measured in host round trips, or not cancelling while the host's reliable verdict is still owed on a live connection, would hold at any frame rate. This is a product change in `encounter_director.gd`, a hot file.
4. **Fence scope:** whether a pending vitals proposal for one participant's creature should refuse every participant's moves, or only that participant's. This is authority design in `encounter_director.gd`.
