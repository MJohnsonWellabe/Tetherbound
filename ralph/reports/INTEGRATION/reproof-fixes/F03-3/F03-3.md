## Warrens Elder (product regression)

The diagnostic message (`f03-wr-run2.txt`) gave `potion_large 0 -> 0; elder valid=true reward_meta=<none> once_id=warrens_once_elder_trailpup; warrens deliveries=[]`. The Elder had its once-id but no receipt.

The cause is in `scripts/combat/encounter_director.gd::spawn_wild`. It applied `opts.completion_reward` only inside the `encounter_id` branch, which is the Stormwood named-encounter path. `burrow_warrens.gd` passes `once_id` and `completion_reward` for the Elder (l.7578-7581) and for the guardian (l.7635-7646), but never an `encounter_id`. The option's own doc comment (l.1500) makes `completion_reward` independent of `encounter_id`.

`grant_clear_reward()` now only sets the clear flag (l.8094). Reading the code, the guardian's clear reward (coins, items, XP) therefore also went unpaid. The guardian smoke was not run before the fix, so that claim comes from code reading; the fixed run proves the payout ("exact authored coin/item receipt", "authored XP", save/load replays nothing). The fix moves the block out of the branch; Stormwood behaviour is unchanged.

Runs: `f03-wr-run1.txt` (reproduced), `f03-wr-run2.txt` (diagnostic), `f03-wr-vault-activity.txt` and `f03-wr-guardian-reward.txt` (pass, including the post-activity production save and load).

## Alpha Galecrest (stale expectation)

The diagnostic message (`f03-ap-run2.txt`) showed the walk engaging, but `enemy=Wild_galecrest_5001_3`, a packmate. Since F03#0 the alpha stands on the pack centre (`stand_at_centre`), so a wandering packmate of this aggressor cluster can reach the trainer first. A wild fight is one creature, so the alpha is not in that fight. The `--hall-decline` path already classifies pack bodies by that name.

The smoke now fights out a packmate that engages first. That fight must be won, and at most two are allowed. The smoke then keeps closing on the alpha with real input. No check was removed: the alpha fight, the once flag, the receipt delivered exactly once, the same five creatures and the save/load are all still asserted. Runs: `f03-ap-run1.txt` (reproduced, gap 11.00), `f03-ap-run2.txt` (diagnostic), `f03-ap.txt` (pass at 19:50:04Z, before `f5648eb8`), and a pass on head `20aaf6ea` (20:12:25Z).

## Local Requests (test harness timing)

1. On this branch the smoke failed 2 of 10 runs (`f03-lr-runs1-10.txt`):
   - Run 3 failed `river_nest paid`. Doss's thanks follows the claim's ledger delta, but `_activate_trainer_prompt` checked `is_open` six ticks after its press, treated the press as missed, and then every retry was blocked by the late reply. The helper now waits up to 60 ticks for the reply its own press opens.
   - Run 5 failed with Juno's Later. The panel was still on the confirmation line and owned input, so the press never reached it.
2. A per-physics-tick trace of that one press (runs 7-10) showed the parsed `menu_cancel` arriving 1-4 ticks after it was sent, and twice only after the release had been sent (`jp=true p=false`). Input flushes parsed events once per main-loop iteration. After the smoke's screenshot capture, one iteration runs several catch-up physics ticks, so the six-tick `_press` could finish before its press was delivered.
3. `_press` now awaits an idle frame after each send. Run 11's trace shows delivery 5 ticks after the send, inside the wait. Without the wait, that delay would have made the smoke fail. A real player's press goes through the same flush and is delivered, so this is not a product defect.

No tolerance was widened. The 60-tick reply wait is a wait for the reply the press itself caused; it is not a retry of a failed check.
