REQUEST 2: real co-op bug in scripts/net/realm_transition.gd (+ session join path). Not fixed by the lane.
  Symptom: after any guest reconnect (a drop + rejoin, or a host restart + rejoin), the HOST's own
  Game.enter_realm stalls exactly 120 s (TIMEOUT_MS) in begin_host() and fails; the host cannot change
  realms for the rest of the session.
  Cause: realm_transition.epoch is a per-process counter bumped by reset() on every Session._teardown().
  begin_host() sends _install_host_move.rpc(epoch, generation, ...) and the CLIENT drops it when
  installed_epoch != its own epoch (line 168; same test in _clear_host_move, line 191). A rejoined guest
  has torn down once more than the host (guest epoch 2 vs host 1 after one drop; 3 vs 1 after a host
  restart plus a drop), so it never acks and _host_move_installed_everywhere() never becomes true.
  _host_move_generation is also not reset by reset(), so a restarted host's generation 1 would be dropped
  by a client that saw generation >= 2 from the previous host process.
  Repro: repro_host_crossing_after_rejoin/ (scenario.json + PROOF.md): host + guest join (epochs 1/1),
  guest drop_link + production_join (epochs 1/2), host enter_realm stormwood -> FAIL after 7192 frames /
  120018 ms. run2_full_scenario_PROOF.md is the same failure inside the full F11#3 scenario.
  Suggested fix (for the owner of realm_transition.gd): the client adopts the host's epoch/generation for
  host-move RPCs (e.g. carry epoch in _joined_sender_policy or the snapshot and set it on join), or drop the
  client-side installed_epoch == epoch test for these authority RPCs (the host already validates the echoed
  epoch in _host_move_installed) and reset _host_move_generation in reset(). Needs a focused two-peer test:
  guest drop + rejoin, then a host realm crossing completes.
  The F11#3 scenario avoids a host crossing after any reconnect so the persistence proof stands on its own.
