Foundation integration required BEFORE activation:
1. Actual host-registered Altar id, reach, same-world/session ownership, stable
   character admission, cooldown and out-of-encounter validation.
2. Authoritative same-record compare-and-swap against expected character
   revision, preserve other character fields, promote inventory + creature +
   receipt atomically, owner save acknowledgement/reconnect recovery. The
   returned revision is a dependency, not an implemented CAS inside this helper.
3. Current typed cap defaults to 10 when no creature mirror exists; unknown,
   reserved or caught-above-cap states refuse rather than invent breakthroughs.
   Live legacy gain_xp and generic candy must honor the admitted cap; this
   checkpoint does not change those unowned consumers.
4. Combat-owned learnset refresh, applicable move/trait unlock mirrors and UI
   signals must be part of or follow successful promotion. Staged level math
   preserves metadata and HP fraction, never revives or heals a fainted creature.
5. Release is the current actual host-owned creature, never an unaccepted sixth
   or declined volunteer. Host ceremony validates eligibility and atomically
   incorporates accepted replacement, roster selection/traversal references,
   existing pending capture/offer receipt and release payout in the same state.
   No post-release separate item grant or UI-only authority fallback.
6. Unchanged spend id with unchanged target/start level/payment is idempotent
   after reload even when the creature level is now different. Reusing the id
   with different intent or multiple matching receipt signatures refuses.
   Receipts are retained; a full authored journal budget refuses new mutations.

Altar UI injection contract (no Game/Session mount authored here):
configure_service(Node) requires station_available(station_key),
quote_essence_spend(station_key, owned_uid),
submit_essence_spend(station_key, request), and
signal essence_spend_completed(spend_id, result).
Quote display fields: ok, creature_uid, level, cap, expected_character_revision,
payments:[{id,name,cost,available}]. All host consumers recompute the quote.
ESSENCE.quote_spend(admitted, character_id, actual_owned_uid,
 character_revision, essence_cfg, progression_cfg) supplies exactly this
 detached display shape from canonical ItemDB/inventory/typed cap. It quotes
 both types for a dual-type creature and one generic Candy option, returns
 no payments at the cap, and validates staged next-level math before quoting.
 The station service still owns actual Altar validation and authoritative CAS.
Submission contains only spend_id, creature_uid, expected_level, payment_item,
expected_character_revision, plus separate station_key. No quoted balance/cap/
cost leaves the UI. Callback only after accepted state is promoted or refusal
is known; closing the panel retains a pending id without invented rollback.
No service means no activation. The panel joins input_owner, keeps a closing
button guard, uses actual five-creature roster and restores HUD/mouse only
when another modal does not own them. Native layout/controller proof pending.

ESSENCE.defeat_payout(host_defeated_row, essence_cfg) calculates exact canonical
type stacks only. Combat validates actual wild defeat/participants/event id.
PROGRESSION.scaled_combat_xp preserves a positive configured trickle. Both
remain unwired until the existing host defeat event stages XP + essence + cap
clamping atomically; rest XP stays on its independent existing path.
PROGRESSION.scaled_party_combat_xp applies the configured participant share
with a positive floor too; use this instead of a second legacy party_share
call which could round a small eligible award down to zero. Eligibility and
recipient cap clamping still belong to the encounter/CAS owner.

ESSENCE.stage_care(admitted, character_id, actual_owned_uid, host_day,
 character_revision, essence_cfg) stages a detached type payout and durable
 care:<character>:<host_day>:<uid>:<amount> receipt. It refuses duplicate UID/day
 awards, counts actual journaled units toward the character/day cap, permits
 at most the remaining configured daily units and rejects conflicting receipts
 or full inventories without mutating the admitted state. Receipt ids use the
 existing F16 care namespace; no extra schema/balance/day counter is added.
 The Den/host owner must validate the actual grooming action and host day, then
 combine existing grooming completion + care award in one CAS. A client cannot
 choose a day or synthesize a grooming entitlement. Host-world day scoping and
 cross-world character admission must be reviewed by the foundation owner
 before activation; this authored helper supplies no new live authority.
