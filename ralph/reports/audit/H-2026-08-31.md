# AUDIT-H — building, survival and care (`ralph/MEADOWS_EXIT_CRITERION.md` §H, H1–H6)

**Audited:** `main` at `453107fb` (LAND-0830J landed 2026-08-30).
**Lane:** AUDIT-H, spawned per `ralph/NEXT_COORDINATOR_FULL_STATE_AUDIT.md`.
**Rule observed:** no game code changed. Every fix this report describes as
"landed" was landed by an earlier lane (T5-CARE / T3-INSTALL) before this
audit began; this lane wrote only test harnesses under `tools/` and this
report. Where this lane found a real defect, it is written down, not fixed.

## Method

Godot `4.7-stable` (CI's pin) installed to `~/godot-bin`; `godot --headless
--path . --import` run twice, clean both times (0 errors). Every verdict
below is either a run of an existing test/smoke file (named, with its exit
result) or a new harness this lane wrote to answer a question the existing
harnesses left open — all under `tools/_probe_t5_*.gd`, all runnable
standalone, all committed on this branch. No config assertions are cited as
evidence by themselves; every PASS below is a played path through the real
`scenes/world/meadows_playground.tscn` driven by parsed physical
`InputEventJoypadButton`/`InputEventJoypadMotion` events through the live
InputMap, or an existing CI-covered smoke test re-run on this SHA.

**Starting point.** T5-CARE (`ralph/reports/handover-T5-CARE-2026-08-30.md`)
gave §H its first evidence and shipped three fixes: (1) a velocity-clamp
fix for a boot-time 7,000,000 m launch that had prevented `smoke_gate_a_
build_segment_meadows.gd` from ever completing a run, (2) a fix so pressing
"interact" near a *refusing* offer (e.g. "Gather deadwood" with the wrong
tool equipped) gives the press back to Build instead of eating it, (3) a
fix so the satchel's "Who eats it?" picker includes the trainer's own row.
This lane's job was to verify those three fixes on landed `main`, not take
them on trust — and to close two gaps T5-CARE explicitly left open: whether
dismantle works at all, and whether a second death produces a second
satchel. Both investigations turned up real, previously-unknown defects,
reported below.

## H1 — "A basic shelter is fast and pleasant to build; modular pieces snap, rotate, dismantle with refund."

### Placement, snap, rotate — PASS, unchanged from T5-CARE

`tests/smoke_gate_a_build_house.gd` (CI-covered, `ci.yml` matrix entry
`smoke: gate_a_build_house`), re-run clean on `453107fb`:

```
paid controller build: 2x2 floor + shared door/walls + four wall-top roofs
controller dismantle: exact middle piece removed; neighbours survive; full refund
build Cancel: ghost cleared and unpaused world control returned
GATE A BUILD HOUSE SMOKE: PASS
```

This also **closes T5-CARE's own open item** "dismantle and refund,
played... worth ten minutes from someone who can watch the highlight": a
generic build piece dismantles and refunds correctly when the player is
positioned the way this test positions them. See below for why T5-CARE's
own repro attempt (and this lane's naive first attempt) failed instead.

### Getting into Build mode — the fix is real but INCOMPLETE. The canonical proof still FAILS.

T5-CARE's fix (`playground_hud.gd::_hammer_opens_the_catalogue()`) makes a
press give up an offer that would **refuse** the player (wrong tool
equipped) back to Build. That fix is present on `main` and does what it
claims — verified by re-reading the code and by the passing smoke tests
above. But T5-CARE's own verification of it was a single spot repro (stand
near a "Gather deadwood" node, confirm Build opens), not a run of the
canonical continuous proof the fix exists to unblock. This lane ran that
proof:

```
godot --headless --path . --script tests/smoke_gate_a_build_segment_meadows.gd
```

**Result: FAIL, 26 real player-driven build steps in (floors placed, both
rear roofs placed, front-left roof placed), on the front-right roof:**

```
FAIL  Build did not open from the controller's own route into the catalogue
      (equipped=hammer, arbiter winner=Prompt offering
      { "label": "Open Door", "distance": 2.77, "priority": 0, "actionable": true },
      fighting=false, trainer_battle=false, arbiter enabled=true,
      input owner=false, paused=false)
GATE A BUILD MEADOWS SEGMENT: FAIL
```

**Root cause, and why it survived T5-CARE's fix.** The fix's rule is
narrower than it needs to be: it only gives the press back to Build when
the winning offer would **refuse** the player. A player's own just-built
door is a **winning, actionable** offer ("Open Door" succeeds), so the same
fix that correctly rescues Build from a refusing gather prompt does nothing
here — the door legitimately wins the press, same as it always did, and
Build is still starved of its only pad route. This is the *same defect
class* T5-CARE called "the worst thing in section H" (an actionable
interactable near the build site silently eats the one input Build has),
now demonstrated on a different object (a door, not a resource node) at a
later point in the same continuous session (re-entering Build after your
own house already has walls and a door). **`smoke_gate_a_build_segment_
meadows.gd` — the canonical proof "a controller can build in the real
Meadows" — has never once completed a full run.**

**Verdict: FAIL.** Placement/snap/rotate/cancel are real and pass on a
narrow-scope smoke test; the *general* claim "the player can always get
into Build mode near the thing they are trying to build" does not hold once
the build session runs long enough to have built anything with its own
interactable (a door). Cost to close: real engineering, not tuning — the
"give the press back to Build" rule needs to become priority-aware
(Build/dismantle owns the press whenever the hammer is the equipped tool
and something is armed or a `_dismantle_target` is live, rather than only
when the competing offer would refuse), or Build needs a way to distinguish
"this offer is more specific/local than the ghost the player is aiming"
from "this offer merely also exists." Estimate: a focused day, including a
second run of the same canonical test to confirm the fix generalises (this
test is exactly the regression guard for it and should be added to
`ci.yml`'s smoke matrix — it currently is not).

### Dismantle range/aim — RESOLVED as a harness artifact, not a game defect

This lane's first dismantle attempt (mirroring T5-CARE's own stance: player
3 m south of the piece, `global_rotation = Vector3.ZERO`) also found
`_dismantle_target == null` and reported FAIL. Diagnosed with
`tools/_probe_t5_dismantle_armed.gd`: `build_placer.gd::_update_dismantle_
target()` casts its ray from the **camera's** screen-centre, not the
player's own facing — the third-person camera sits ~4 m further back than
the player, so a "3 m standoff" the player judges as close is actually
close to the full 8 m `DISMANTLE_RANGE` measured from the camera, and the
ray fell just short. `smoke_gate_a_build_house.gd`'s own working dismantle
(above) confirms the mechanic is sound once the camera is actually aimed at
the target. **This resolves T5-CARE's own uncertainty** ("I am not
confident enough to call this a defect rather than my aim being wrong") —
it was the aim.

### Two NEW, real defects this audit found while chasing the above

**(a) `build_dismantle` and `inventory` share joypad button 3 (Y), and
dismantle is only wired up while a piece is actively armed — so pressing Y
near an unarmed piece silently opens the satchel instead of dismantling,
and nothing tells the player why.**

`build_placer.gd::_physics_process()` returns immediately at its own line
220 (`if armed == "": ...; return`) whenever `pending_build == ""` — which
is the ordinary state right after finishing a placement, i.e. exactly the
moment a player who just built something would try to remove or fix it.
With that early return, the dismantle-handling code at line 270+ never
runs, so the Y press is never consumed by `build_placer.gd`. `input_glyph.
gd:51` confirms Y is the labelled glyph for `"inventory"` on gamepad, and
`game_menu.gd`'s shortcut loop (line 706) is exactly what catches the
un-consumed press and opens the satchel/`GameMenu` shell instead — which
pauses the tree (`game_menu.gd:349`).

Reproduced directly: `tools/_probe_t5_falldrop2.gd` places a `creature_bed`
(staying unarmed afterward, matching `tools/_play_t5_deaths.gd`'s own
sequence), stands the player 3 m off facing it, and holds Y for one second:

```
T5FALL2> post-dismantle pos (30.0, 0.07, -39.0) on_floor=true carried=false
         locomotion_enabled=true tree_paused=true
T5FALL2> input owner: GameMenu
```

The tree stays paused forever in this synthetic-input harness because
nothing sends the close press (`menu_cancel`/B) afterward — a real player
would press B and get their movement back, so this is not a genuine
soft-lock in real play. But the substitution itself is real and
undiscoverable: **the player believes they are aiming at "the piece I just
placed" and pressing "remove it," and instead the satchel opens with no
explanation, every single time nothing is currently armed.** The *only*
way to make dismantle live is to first re-open the build catalogue and
select (arm) some piece — including one you have no intention of
placing — which is exactly what `smoke_gate_a_build_house.gd`'s passing
run does, and exactly what this lane's own failing first attempt, and
T5-CARE's, did not know to do.

Cost to close: small and well-scoped — either give `build_dismantle` its
own unshared physical button (the owner's 14-button budget is already
described elsewhere as full, so this needs an owner call on what to bump),
or make dismantle live whenever the hammer is the equipped tool regardless
of `pending_build`, matching how a real player would expect "I have my
hammer out, I am aiming at a wall, Y removes it" to work without an
unrelated arm-then-aim step. A few hours once the direction is chosen.

**(b) `creature_bed.gd` places its body with no `StaticBody3D`/
`CollisionShape3D` at all — unlike every other placeable — so a creature
bed can never be dismantled by any raycast, regardless of stance or aim.**

`scripts/build/build_piece.gd:80-81` and `scripts/build/camp.gd:252-253`
both construct a real `StaticBody3D`+`CollisionShape3D` for the piece they
place. `scripts/build/creature_bed.gd` (`extends Node3D`) has no such code
anywhere in the file — confirmed by direct inspection, not inference.
Verified at runtime with `tools/_probe_t5_dismantle_armed.gd`: even with
the camera correctly aimed and the piece well within `DISMANTLE_RANGE`
(6.9 m of an 8 m budget), a raw physics ray with the player excluded
returns an **empty hit** at the creature bed's exact position — there is
genuinely nothing there for a raycast to find:

```
DISMANTLE-ARMED> ray hit (player excluded) = {  }
```

This matters specifically because `creature_bed` is one of only **two**
piece types the chapter's opening ladder requires the player to build
(`home_built`, `creature_bed_built`) — it is not a decorative extra. A
player who places their creature bed in the wrong spot, or wants to move
it, has **no way to remove it**: not from a bad stance, not from a good
one. Cost to close: small, mechanical, and precisely located — add the
same `StaticBody3D`+`CollisionShape3D` pattern `build_piece.gd`/`camp.gd`
already use, sized to the bed's own footprint. An hour or two including a
regression test.

### Ghost readability against grass — unchanged from T5-CARE, not re-verified

T5-CARE's frames (`shots/t5-care/ghost-camp.png`, `ghost-creature-bed.png`)
are real, `capture_check`-clean renders already showing the defect (a teal
wireframe in the grass's own hue family, positioned so the over-the-
shoulder camera puts the player's own body in front of it). This lane did
not re-render; nothing about landed `main` suggests it changed, and the
finding is visual rather than a played-path question this lane's harnesses
answer any better than the existing frames already do.

**H1 rollup: FAIL.** Placement/snap/rotate/cancel work; the single most
central verb of the chapter's build ladder — reliably reaching Build mode
across an extended real session — still does not, on the game's own
canonical proof; dismantle works for ordinary pieces once aimed correctly
but is completely unreachable for one of the two pieces the opening
requires; and a silent, undocumented button collision substitutes the
inventory screen for dismantle whenever nothing is currently armed.

## Multiple death satchels persist — RESOLVED (was T5-CARE's open gap)

T5-CARE could not stage a second death: `tools/_play_t5_deaths.gd`'s 120 m
drop reported "landed on frame 11 at -0 m/s, health 100" twice and the lane
ran out of runway to diagnose why, leaving this **the single largest open
gap in section H's evidence**.

**Root cause found: it is the SAME button-collision bug as H1(a) above, not
a physics or fall-damage defect.** `_play_t5_deaths.gd` runs a dismantle
attempt (with nothing armed, matching the repro above) immediately before
its two falls. That dismantle attempt opens `GameMenu` and pauses the
`SceneTree`; the harness never presses B to close it, so every frame after
that — including both drops — executes with the world frozen. Confirmed by
`tools/_probe_t5_falldrop2.gd`, which reproduces the identical dismantle
sequence and shows the player's position and velocity frozen bit-for-bit
across 20 traced frames post-teleport, with `tree_paused=true` and
`INPUT_OWNER.current() == GameMenu`.

With the dismantle step removed, `tools/_probe_t5_deaths_clean.gd` produces
a clean, real, played result:

```
death 1 — dropped from 120m carrying 10 wood; landed on frame 154 at 92 m/s, health after = 100
  death satchels now: 1
death 2 — dropped from 120m carrying 11 wood; landed on frame 154 at 92 m/s, health after = 100
  death satchels now: 2
  satchel 1 at (30.0, 0.1, -40.0)
  satchel 2 at (48.0, -4.5, -28.0)
VERDICT: PASS — two deaths left two satchels; neither replaced the other.
```

92 m/s is well above `vitals.json`'s 34 m/s lethal-landing threshold; both
falls genuinely killed the player (satchel count goes 0→1→2, not 0→1→1),
and health reading 100 afterward is the respawn healing the trainer, not
evidence the fall was non-lethal. **Verdict: PASS**, the hard rule holds —
two independent satchels at two independent positions, neither overwriting
the other — closing T5-CARE's largest remaining gap. Cost to close: none —
already passes; the only remaining cost is that this evidence lived behind
an unrelated bug until this audit separated the two.
