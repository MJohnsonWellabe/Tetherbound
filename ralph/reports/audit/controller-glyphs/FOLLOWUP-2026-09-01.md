# BACKLOG-VISUAL-CONTROLLER-GLYPHS / BACKLOG-VISUAL-INPUT-GLYPH-LANGUAGE — 2026-09-01

**Root cause: a capture-harness artefact, not a live-game defect.** The
runtime HUD/UI code already draws live, device-aware controller-first glyphs
everywhere the census's evidence covers. The three specific capture tools
that produced `hud_full.png` (defect 148), the five `survey_combat.gd` frames
(defect 129), and `ui_explore_prompt.png`/`ui_inventory.png`/
`ui_inventory_selected.png` (defect 148) never simulated a connected gamepad,
so every one of those renders fell back to the game's own keyboard/mouse
default — a default that is correct under `xvfb-run` (no joypad exists in
that container) and wrong for the ROG Ally (an always-connected XInput pad,
CLAUDE.md's primary target). This report patches the three capture tools;
**no gameplay/UI code changed**, per CLAUDE.md's "do not rewrite a working
system just to produce a diff."

## What the census claimed

`ralph/reports/audit/VISUAL-CENSUS-2026-08-31.md`:

- **#129** (`survey_combat.gd`'s five combat frames): "Keyboard and mouse
  glyphs in a controller-first project... `01-approach.png` prompts `E
  Engage Bramblebun`; `02`–`05` show `F`, `C` and mouse-button icons on the
  ability tray."
- **#148** (`hud_full.png` plus the `capture_ui_suite.gd` inventory trio):
  "The exploration HUD shows keycaps only (`M` Map, `I` Satchel, `R` Call
  Out, `C` Change Creature, quickbar slots `1`–`5`) with **no gamepad glyph
  anywhere**... the tooltip uses pictorial glyphs including a **mouse-click
  icon with no controller equivalent**... Two of these contradict each other
  on one screen."

Ranked #5 in the census's own "what a follow-up session should do first"
list as "the only finding in the census that two blind critics reached
independently from different rigs, and a direct `CLAUDE.md` hard-rule
violation ('controller first') rather than a matter of taste."

## What the live game code actually does (read, not rendered)

`scripts/ui/input_glyph.gd` is a mature, already-tested device-aware glyph
resolver: `icon(id)` auto-detects the live input device via
`using_gamepad()` (`Game.last_input_was_gamepad()`, tracked live off the
*last input event type* — a real keypress or a real joypad-button event
flips it, per `autoload/game_state.gd`'s `_unhandled_input`) and returns the
matching Kenney glyph PNG, falling back to a bound-key/bound-button text
label only for the handful of ids with no art sourced yet
(`backpack_assign` = L3/J, documented in-line as deliberate). Every call site
the census's frames touch already routes through it:

- `scripts/ui/playground_hud.gd::_legend_entry()` / `_exploration_legend_text()`
  — the persistent M/I/R/C legend and the five hotbar slots (`_update_hotbar`,
  `INPUT_GLYPH.icon(HOTBAR_ACTIONS[i], ...)`).
- `scripts/world/prompt_arbiter.gd::format()` — the interact prompt
  (`INPUT_GLYPH.icon("interact")`), read by both the exploration prompt and
  the combat "Engage X" line.
- `scripts/ui/combat_hud.gd` — the Actions row (`quick`/`charged`/`throw`/
  `party_cycle`/Throw/Cancel), all `INPUT_GLYPH.icon(...)` calls.
- `scripts/ui/tab_backpack.gd::_verb_hint()`/`_describe()` — the backpack
  detail-column verb legend, all `INPUT_GLYPH.icon(...)`/`_verb_glyph(...)`.

`GLYPHS` in `input_glyph.gd` has a `gamepad` entry for every id these call
sites use, including `quick`/`charged` (mouse-left/right on keyboard, RT/LT
on pad) — there is no glyph in the live game that shows a mouse icon with no
gamepad half. The one prior real gap in this system —
`party_cycle`/`hotbar_*` rendering the legend's `C` as a bracket-text
fallback beside real `M`/`I`/`R` keycap art — was root-caused and fixed
already, landed on `main` in commit `0ff41fe1` (2026-08-30, the day *before*
the census branched from `721893a4`), documented in `input_glyph.gd`'s own
`party_cycle` comment as "the persistent exploration legend rendered `M` /
`I` / `R` as real keycap images beside a bare, greyed `[C]`."

## Why the census still saw keyboard-only glyphs anyway

`autoload/game_state.gd:426`: `_last_input_was_gamepad: bool = not
Input.get_connected_joypads().is_empty()`. On the ROG Ally this is `true`
from frame one, before the player has touched anything, because its pad is
an always-connected XInput device. Under `xvfb-run` (every capture tool in
this repo, including the census's) `Input.get_connected_joypads()` is always
empty, so this initialises `false`, and unless a tool explicitly flips it or
simulates a real joypad-button event, every frame it renders shows the
keyboard/mouse half of every glyph — correctly reflecting "no controller
connected to this container," not reflecting what the owner's own hardware
does.

This is not a new discovery: it has independently been root-caused and
worked around at least three times already on `main`, and each fix only
covers its own tool:

- `tools/_capture_ui_survey.gd::_pin_owner_device()` (added in the same
  `0ff41fe1` merge as the `party_cycle` fix above) — pins
  `_last_input_was_gamepad = true` for its whole run, with an explicit
  header: *"the round-1 blind critic read the resulting keycaps as
  CLAUDE.md's 'Controller first' hard rule being violated across the whole
  interface, and the single largest finding in that report was spent on a
  device the owner's hardware never presents."*
- `tools/capture_ui_suite.gd` shot 18 (`ui_inventory_focus`) — pins the flag
  true for one single frame, "forced gamepad-glyph mode."
- `tools/capture_hud_op21.gd` — injects a real `InputEventJoypadButton`
  (A press/release) rather than setting the private var directly, with its
  own header explaining the identical mechanism.

None of those three fixes reach the tools that actually produced the
census's cited evidence:

| census frame(s) | tool | pinned gamepad before this fix? |
|---|---|---|
| `hud_full.png` (defect 148) | `tools/capture_exploration_hud.gd` | no |
| `01`–`05` combat frames (defect 129) | `tools/survey_combat.gd` | no |
| `ui_explore_prompt.png`, `ui_inventory.png`, `ui_inventory_selected.png` (defect 148) | `tools/capture_ui_suite.gd` | only shot 18, not these three |

So the census's own evidence-gathering ran three of the repo's capture tools
that predate (or, for `capture_ui_suite.gd`, only partially applied) the
already-established fix, and both blind critics correctly read what was on
screen — keyboard keycaps and a mouse-click icon — and correctly flagged it
against a controller-first hard rule. The pixels were real; the game state
that produced them (no controller connected) is one the owner's own hardware
never reaches.

## The fix

Added the same one-line pin the other three tools already carry, to the
three that were missing it:

- `tools/capture_exploration_hud.gd` — pinned right before `_seed_demo_state`,
  covering `hud_full`/`hud_sprint`/`hud_lowstam`/`hud_hungry`/`hud_lowhp`.
- `tools/survey_combat.gd` — pinned right after the starting-orb grant, before
  the first capture (`01-approach`), covering all five combat frames.
- `tools/capture_ui_suite.gd` — pinned once at the top of `_run()`, covering
  `ui_explore_prompt`/`ui_inventory`/`ui_inventory_selected`/every later
  shot, not only shot 18 (whose own explicit pin is now redundant but left in
  place as in-line documentation of that shot's specific purpose).

No gameplay/UI code changed. `docs/decisions/` gets no new entry — this is a
tooling correction, not a design decision.

## The sub-claims checked and not carried forward as separate defects

- **"Mouse-click icon with no controller equivalent."** Checked `GLYPHS` in
  `input_glyph.gd` for any id whose only art is a mouse PNG: none exists —
  `quick`/`charged`/`build_place`/`build_cancel` all carry a `gamepad` entry
  alongside their mouse one. The mouse-only render the census saw was the
  unpinned-device default, now fixed above.
- **"Two on-screen instructions for the same action contradict each other"**
  (`ui_inventory_selected.png`: "pick a stack up with [confirm-icon], then
  press a slot" next to "J / [L3] Put on the quick bar"). Read
  `tab_backpack.gd::_describe()`/`_verb_hint()` directly: these are two
  *different* verbs (`confirm` = pick up/put down a stack; `backpack_assign`
  = bind it to a quick-bar slot), not one action described two ways. The
  apparent inconsistency is real but narrower than "contradiction": most of
  this file's hints show one auto-detected device glyph via `icon()`
  (matching the legend/hotbar/prompt convention), while `_verb_glyph()`
  (used only for `backpack_assign`/`backpack_drop`/`backpack_split`)
  deliberately shows *both* halves side by side ("key / [pad]"), a pattern
  OW1's own header explains was chosen so the backpack's verb legend "has to
  name BOTH halves of a dual binding the way the pause menu's own footer
  does." That is a legitimate, if inconsistent-looking, second display
  convention already present in the code, not a bug this pass introduced or
  can attribute to the device-pinning root cause. Left as-is: unifying every
  glyph call site onto one display convention is real work
  (`BACKLOG-VISUAL-INPUT-GLYPH-LANGUAGE`'s own closing-cost note calls the
  full unification "data/config" work, separate from "redrawing the two
  unreadable glyphs"), out of scope for this bite-sized capture-tool fix, and
  not the hard-rule violation the census's headline claim was about.
