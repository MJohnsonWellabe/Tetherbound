# BACKLOG-VISUAL-CREATURE-ALBEDO-CLIPPING — investigation, 2026-09-01

**Does not reproduce.** Direct pixel measurement on a fresh render, from the
exact tool and exact textures the census cited, puts all four defect-63
frames under 2% clipped in either direction — not the 26–42% the census
reported. This report is the evidence for that, not a code fix: nothing in
`scripts/creatures/creature_body.gd`, `tools/_capture_creature_roster.gd`, or
any of the four species' textures changed on this branch.

## Before touching anything: the ledger's own warning

`ralph/VISUAL_LEDGER.md`'s "THE EXPENSIVE ONE" records that three earlier
creature-visual rounds spent their top finding on a capture-stage exposure
bug (ambient+key stacking on self-lit creature materials, measured 2.3x
over-exposure) rather than a real art defect, and that the fix — calibrating
the stage's ambient/key/rim against the floor's own known albedo — already
landed in `tools/_capture_creature_roster.gd::_build_environment()`. That
calibration comment is present, unchanged, in this defect's own capture tool,
confirmed by diffing the tool against the census's own branch point
(`721893a4..origin/main` touches only the alpha-scale/pipwing-lineup camera
work already landed by other lanes, not the lighting rig). So the exposure
fix this ledger describes was already in place *when the census ran it* —
the question was whether something else (the shiny system, a per-species
texture, or a fresh capture-stage bug) reintroduced clipping on top of it.

## What was checked, in order

1. **Static texture analysis** (no Godot). Measured the committed
   `_base_color_shiny.png` / `_base_color_vivid.png` files directly:
   duskhush-shiny's texture has 0.19% of texels ≥240 (not bright), galewisp's
   vivid has 0.31% ≥240 (not bright), veridian's vivid has 23.7–27.7% ≤30 (a
   real, and per `shiny_colourways.json`'s own comments *deliberate*,
   near-black "charcoal hide, emerald veins" design), burrowback-shiny's
   texture has 62–67% ≤10–30 (also deliberate — third design pass explicitly
   pushes the body "near-black" so the pale bronze plates read by value
   contrast). None of the four textures is anywhere near 26–42% *literally*
   clipped in isolation.
2. **Rule-level simulation** of `tools/repaint_creature_textures.py`'s HSV
   pipeline (imported directly, run against the real source textures and the
   real `shiny_colourways.json` rules) reproduced the committed PNGs exactly
   (byte-for-byte-equivalent stats: duskhush-shiny mean 177.7, burrowback-shiny
   27.7% ≤5, veridian-vivid 5.48% ≤5, galewisp-vivid 167.8 mean) — confirms
   the repaint tool is a pure function of inputs already understood, and
   nothing in it is silently pushing values further than the source rules say.
3. **A real render.** `tools/art_pipeline/setup.sh godot` fetched Godot
   4.7-stable (pinned, matches CI); ran the import pass
   (`godot --headless --path . --import`, ~9 min) and then the cited tool
   itself, verbatim invocation from its own header:

   ```
   xvfb-run -a -s "-screen 0 1280x800x24" godot --path . \
     --rendering-driver opengl3 --resolution 1280x800 \
     --script tools/_capture_creature_roster.gd
   ```

   All 70 frames rendered clean (no "WARN no model found" fallback lines).
   Measured every output frame's pure-white (`RGB≥250` all channels) and
   pure-black (`RGB≤5` all channels) share:

   | frame | this branch, fresh render | census |
   |---|---|---|
   | `14-duskhush-shiny.png` | white 0.59%, black 0.16% | white 31.9% |
   | `03-galewisp.png` | white 0.79%, black 0.15% | white 26.4% |
   | `07-burrowback-shiny.png` | white 0.02%, black 1.87% | black 41.9% |
   | `17-veridian.png` | white 0.12%, black 1.44% | black 37.9% |

   The worst frame *anywhere in the 70-frame roster* is
   `07-burrowback-shiny-rear.png` at 3.78% black — still an order of
   magnitude under every one of the census's four numbers, and every other
   frame is under 2%. Two regression-check control frames (`01-terrapup.png`,
   `09-tuskroot.png`, not cited by the census) also came back clean
   (white 0.78%/0.00%, black 0.24%/0.56%). Frames committed under `shots/`
   in this report directory.
4. **Visual read.** All four frames render as intended: duskhush-shiny is a
   pale ghost owl with its dark frost-barring pattern intact (matches
   `shiny_colourways.json`'s own design note — "the largest value gap
   available on this species"), burrowback-shiny is a black-and-cream badger
   with visible face, claws and plate detail, veridian shows a dark stag with
   legible antler branching and a green glow accent. None reads as a flat
   cutout or a hole.
5. **Cross-check against the census's own committed evidence.** The census
   branch committed `VISUAL-CENSUS-2026-08-31-shots/sheets/03-roster-world.jpg`
   — the actual contact sheet built from the same capture run the critic
   measured. Located and cropped the tiles for all four species (grid math:
   `tools/contact_sheet.gd` is `COLUMNS=3`, frames sorted by filename, `-`
   sorts before `.` so `NN-species-rear.png` precedes `NN-species.png`
   alphabetically — verified against the fresh 70-file listing before
   trusting the crop). Every one of the four tiles shows a normally-lit,
   legible creature — not a 30–40% flat white or black region. If the
   critic's frames really carried that much literal clipping, it would be
   visible at contact-sheet-thumbnail scale; it is not.

## Conclusion

**Capture bug, real material bug, or shiny-system bug? None of the three —
this defect does not reproduce against current `main`.** The four textures
carry real (and two of them, per their own design comments, *deliberate*)
value extremes, but the render — with the already-calibrated stage — brings
all four back under 2% literal clipping, an order of magnitude inside the
26–42% the census reported and consistent with what the committed contact
sheet already shows. The most likely explanation is that round 2's precise
-looking percentage table was not produced by an actual pixel-counting
script (none is named or linked in the critique, unlike this report's
reproducible measurement) — the census's own method section describes the
critic as "a fresh sub-agent... given the sheet, the individual frames," not
a script. Nothing else changed between the census's branch point and now
that would explain a fix (checked: no commits since `721893a4` touch
`creature_body.gd`'s variant-tint path, `creatures_visual.json`, the four
species' textures, or the roster capture stage's lighting).

**No code, data, or texture change was made on this branch** — CLAUDE.md:
"Do not rewrite a working system just to produce a diff." The residual
0–4% clipping visible above is real, non-zero, and still short of the
Palworld ~0% bar, but is not what defect 63 described and is not itself a
new bite-sized finding worth a speculative lighting change against a shared
capture tool other in-flight lanes depend on for scale/grounding numbers
(`BACKLOG-VISUAL-ALPHA-SCALE`, `BACKLOG-VISUAL-PIPWING-LINEUP-SCALE`, both
already landed on `main` and touch this same file).
